# belay

A personal issue tracker for Claude Code work, and the Belay app around it: a CLI (`src/`), the local Next.js app (`web/`: projects, grills and courses), and the `belay` Claude Code plugin with its channel bridge. Domain terms are defined in `CONTEXT.md`; the app's vocabulary is in `web/CONTEXT.md`.

## Don't start servers

Never run `belay serve`, `pnpm dev`, `next dev` or `next start`. The user starts and stops servers. When something needs checking in the browser, say what to look at and let the user run it.

## Layout

- `src/` is the CLI. It runs on Node 24 type-stripping (no build step) with TS 7, and `yaml` is its only runtime dependency, pinned exactly: issue files must re-save byte for byte, so a new version needs the round-trip tests run against a copy of the data. `belay digest` runs in every SessionStart hook and `belay statusline` after nearly every message, so a heavier dependency or a build step slows every session.
- Core finds extensions by their `extensions/<id>/belay.json` (`src/extension-ids.ts`, cached by mtime): id, name, summary, mark, owned fields, site paths, sessions folder and whether those go into the data dir's history. Core code names no extension; what it needs comes from there. Installed is `extensions/installed.json` (gitignored; with none, nothing is installed), changed only by `belay extension install|uninstall` (`src/install.ts`: its pnpm and claude steps are injected, so tests run neither, and the record is written last on install and first on uninstall). `belay serve` restarts Next when it exits leaving `<data>/.run/serve-restart`. An extension is self-contained in `extensions/<id>/`: `cli/`, `web/`, `bridge/`, `plugin/` (its Claude Code plugin, named `<id>`), `test/` (CLI tests at its top, `site/`, `bridge/` and `plugin/` for the other runners) and a `package.json` whose peers are the site's react, next and UI packages. `src/generate.ts` (`scripts/generate.ts`, run by `belay serve`, `pnpm dev` and `pnpm install`) writes the gitignored files from the installed ones: route stubs in `web/src/app/(browse)/(<id>)/` re-exporting `extensions/<id>/web/`'s route files, `src/extensions.generated.ts` and `web/src/lib/extensions*.generated.ts` (each layer's manifests) and `web/tsconfig.extensions.json` (the `include` `web/tsconfig.json` extends). It deletes only stubs headed as generated. The CLI needs `src/extensions.generated.ts`, so a fresh clone runs `pnpm install` before any `belay` command, then `belay extension install <id>` for each extension it wants. The repo's checks expect every bundled extension installed.
- An extension's CLI parts are slots on its `extensions/<id>/cli/manifest.ts`: subcommands, `belay search` hits, digest lines, help lines, the dashboard's linked-file kinds and a `disabled` hook run as it's switched off. Each loads by a literal `import()` only when a command needs it. Core commands resolve before the settings are read, and only handlers read them, never a module's top level. Its owned issue fields (grill's `grill` and `plan`, in its `belay.json`) live in `Issue.extra`, read with `owned(issue, id)`, and become `add`/`edit` flags while it's active. Its tests live in `extensions/<id>/test/`.
- Whether an extension is active is `isActive` in `src/extensions.ts`: installed, and either switched on (the default) or one of its sessions attached. Its site paths are `paths` in its `belay.json`, which `web/src/proxy.ts` 404s while it's inactive. The bridge reads Installed itself (`bridge/extensions.mts`) and loads each installed extension's compiled `bridge/<id>.mjs` (`bridge/kinds/index.mts`), every one on by default; a test checks both against the CLI's.
- The repo is a pnpm workspace (`pnpm-workspace.yaml`: `web` and `extensions/*`, one root lockfile). `web/` is a Next 16 package with its own `package.json` and TS 5. It imports `../src/*.ts` directly. `belay serve` builds and starts it on 4747. `web/AGENTS.md` covers the app, bridge and plugin; its top block is managed by Next: read the docs it points to before writing Next code, because this Next version differs from what you know.
- `bridge/` is the channel bridge's TypeScript source, compiled by `pnpm build:bridge` in `web/` into `plugin/bridge/`, with each extension's `bridge/*.mts` into `plugin/extensions/<id>/bridge/` (the tree mirrored, so their imports of core and zod resolve inside the plugin). `plugin/` is the `belay` plugin (only the MCP server and channel); the local marketplace in `.claude-plugin/` lists it and each extension's plugin (`grill`, so `/grill:grill`). Claude Code runs plugins from a copy in its cache, so the bridge finds the clone by `BELAY_REPO` (which `belay claude` sets), then its own folder, then the `belay` marketplace's directory. `belay claude` and `belay learn` (`src/launch.ts`) start Claude Code with its channel loaded. The root's MCP SDK and zod dev deps are only for typechecking the bridge. `plugin/` pins the same exact `yaml` as the root, for the bridge's settings reader.

## Rules

- Every data write goes through `src/ops.ts`. Each op re-reads the file just before saving it. A write that bypasses the ops can overwrite a note Claude or the CLI appended a moment earlier.
- The dashboard's data operations are a subset of the CLI's (the user's rule). Before adding a write to the dashboard, add it to the CLI.
- Only an extension's own folders, each layer's built-in list and `scripts/` may import its code; `test/import-rule.test.ts` enforces this, and keeps `scripts/import-rule.ts`'s `OWNED_UNMOVED` and `test/import-pending.json` empty: never add to them.
- Put logic in `ops.ts` or pure helpers in `src/` and test it with `node:test`. There are no UI tests, so logic inside components or server actions goes untested.
- Never test against the real data dir (`~/Belay`). Its git history is local only, and lessons, `.run/` and unfinished grills aren't tracked, so a bad write may not be undoable. Point `BELAY_DATA` at a temp copy.

## Checks

- Repo root: `npm test` and `npm run typecheck`
- `web/`: `pnpm typecheck`, `pnpm lint`, `pnpm test:site`, `pnpm test:bridge`, `pnpm test:plugin`
- After a fresh clone: `pnpm install` at the root, `npm install` in `plugin/`, then `belay extension install` for grill, learn and review.
